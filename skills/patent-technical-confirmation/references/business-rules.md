# 授权技术条款摘编

OasisIntWrite，2026-11-07。以下是获授权自编规则的具名技术条款，未复制历史治理、收据、案例或评价答案。修改：本包独立合同与核心规则规定普通材料输入、身份、保存、状态和累计边界；条款里的前序品牌只在明确链式任务适用，不能成为独立前置。章节号用于精确核对，缺失的输入/运行/治理条款由本包合同替代，不要求回读源项目。技术来源、原草案效力及未验证边界见sources.json。

<a id="business-3-1"></a>
### 3.1 反馈逐项处理

为每项可分辨意见设本节点追踪编号`opinion_id`，并保留原话或必要片段、输入ID、定位和源哈希。重复表达可以归并，但保留所有来源及差异；一条反馈涉及多事项时拆为子项关联同一来源，不把相互矛盾意见“去重”掉。

每项归入下列用途之一或多项：事实确认／纠正、技术补充、机理解释、效果／数据、范围／回退偏好、表达偏好、拒绝／不采用、未回答／不明确。分类用于组织，不能替代实质判断。

先关联既有`tp_id`、`solution_id`、`macro_id`、`feature_id`或`te_id`及上游问题编号。上游缺ID时登记缺失；可为新增追踪项明确创建编号和依据，但不能伪装成已继承ID。不得静默重编旧ID；确需修订时登记旧值、新值、原因、修改节点和影响。

反馈者、反馈时间仅按输入实际提供信息登记；未知则明确未知，不伪造参会人员、发明人身份、会议已举行或签字确认。身份不明影响关键确认时保留警示。

<a id="business-3-2"></a>
### 3.2 规范表述的正向要求

规范技术表述应尽可能说明：

- **对象与场景**：哪种部件、材料、步骤、数据对象或使用条件；
- **技术关系**：连接、位置、依赖、交互、时序、因果、转换或协同关系；
- **手段与动作**：怎样实现、如何配合、触发与终止条件；
- **条件与边界**：适用对象、参数、单位、方向、范围和例外；
- **功能与效果**：该手段直接发挥什么作用、产生什么结果及其依据。

整理口语、统一已有术语、展开有明确指代的省略，必须保持否定、程度、条件、顺序、数量、限制和不确定性。“可能”“暂定”“还没试验”“只有这种工况”不得改成确定事实或无条件效果。

不要求每句话凑齐全部字段。只转换材料已支持的内容；缺失部分分别列为待确认或明确标记的模型建议。算法／控制事项应明确可获知的输入、处理、输出、依赖及触发关系，不能只换成更抽象的功能口号。

有多种合理解释时分别列出候选表述、歧义位置及能消除歧义的具体问题，不直接选最有利于保护的版本。不得用“其他等同结构均可”扩大原意见。

<a id="business-3-3"></a>
### 3.3 追问的可回答性

每个追问包含：当前理解、缺少的具体事实、为什么影响正式撰写、希望返回的材料或说明。问题应能由发明人回答，例如“连接件A与B是固定连接还是允许相对滑动？请说明连接位置及运动约束”，而非“请确认技术方案是否合理”。

优先追问独权相关实体／关系／手段、可实施路径、效果成立条件及影响修改的矛盾；不要求发明人直接回答“是否具有创造性”等专业最终结论。不得用诱导性是非问题把模型假设包装成已认可方案。

<a id="business-4-1"></a>
### 4.1 内容可信状态

沿用V3.4.0：`source_fact`、`confirmed_fact`、`reasoned_inference`、`hypothesis_to_verify`、`excluded_from_formal_text`。来源状态与证据验证程度分别记录，不使用一个“已确认”覆盖二者。

登记`confirmed_fact`必须同时有：明确的技术对象／命题、针对该命题的具体确认、可定位技术依据或具体技术说明、实际反馈来源，且不存在影响该命题的未解决冲突。具体结构确认不以实验报告为一律前提；但只有“效果很好”“方案没问题”等结论，不足以确认机理、效果幅度或参数范围。

以下均不能升级为`confirmed_fact`：未回复、沉默、笼统同意、代理人自己的整理、运行偏好、模型置信度高、缺乏技术依据的效果结论、尚有实质矛盾的反馈。

原为模型补齐的内容，在收到满足上述条件的真实确认后才可升级；保留原`model_completed`来源、补齐登记和新增确认链，不能擦除生成历史。人类确认的`content_origin=human_confirmed`不替代原始技术依据定位。

本标准的意见处理状态使用`confirmation_status`：`pending`、`partial`、`confirmed`、`rejected`、`conflict`。它描述具体意见／事项的处理，不是全链`trust_status`或警示生命周期；`rejected`也不代表对应技术事实必然为假。

<a id="business-4-2"></a>
### 4.2 技术效果与数据

每项效果应关联`te_id`、特征或组合、机理、成立条件、指标／测量方法和证据。证据状态按T3记录已验证、直接记载、合理推导或待验证，并补充该状态的来源说明。

- 发明人解释机理，只确认其实际说明的内容，不能自动推成试验已验证。
- 输入提供数据时记录实验／仿真／计算／观察类别、对象、条件、方法、单位、参照基线、结果和局限；未提供项明确缺失，不用常识补数值。
- 数值缺单位、上下界依据不足、只给单一实施点、缺比较对象、图表相互矛盾时，分别提示其用途限制；不得自行构造区间、百分比或最优点。
- 一种工况结果不推广到全范围；仿真不写成实测；效果期望不写成已取得效果。
- 没有实测数据不等于技术内容必然不可用，可按有来源的结构事实或明确标记推导继续撰写建议；但不能编造定量验证。

<a id="business-4-3"></a>
### 4.3 范围、回退与专业判断

记录保护范围偏好、宽／中／窄层级、从属回退选择、最接近现有技术候选及人工最终判断状态。发明人希望“覆盖所有方式”是范围诉求，不是所有替代方式均可实现的证据。

对新增替代结构、材料、算法或步骤，分别核对具体技术说明、同问题／效果关系及当前说明书支持。证据不够时输出建议限缩、补充说明或人工返工，不直接纳入确认事实。

不替用户、专利专业人员或审查员作最接近现有技术最终判断；不把本次技术确认称为授权保障、创造性确定或正式提交批准。

<a id="business-5-2"></a>
### 5.2 核心结果的六组内容

| 必需内容 | 每项至少能够表达的内容 |
|---|---|
| `technical_confirmation_matrix` | opinion_id／上游问题、关联稳定ID、原话定位、当前基线、规范技术表述、确认状态、trust_status、依据及下游影响；覆盖技术问题、必要特征、元关系、手段和机理 |
| `effect_evidence_confirmation` | 关联te_id和特征组合、效果表述、机理、条件、指标／单位／方法、证据类别与状态、定位和用途限制；缺项不伪造 |
| `confirmed_change_instructions` | 逐项可执行技术修改指令，字段与约束见§6；表名不意味着每条建议均已确认，必须逐条标明采用条件 |
| `technical_evidence_gaps`及不采用内容表 | 缺什么、影响什么、需要谁补什么；哪些内容不得当确认事实或进入正式文本及其原因、来源和重新采用条件 |
| 人工判断状态 | 范围选择、回退路径和最接近现有技术候选的人工判断状态；未决事项不替人工决定 |
| 未完成确认及模型补齐 | 未回复／部分／矛盾事项，模型补齐范围、依据、假设、置信度、影响章节、人类确认状态及风险影响 |

不存在内容的表也显式说明“无本次新增”“上游未提供”或具体原因，不将缺失伪装为空表通过。原话审阅定位可以为页／段／图／权项／文本块及句序；引用片段应足以证明对应表述，不能只给文件名。原话定位与规范表述定位必须分别记录。原输入绑定其来源文件完整原始字节SHA256、片段SHA256和明确的片段字节约定；规范表述在当前主Markdown中记录本文件内位置、片段SHA256及其字节约定。该主Markdown的终稿完整原始字节SHA256由调用方或评价记录在文件冻结后外部绑定，不回写自身，不因此增加第二个业务输出文件。原话定位只能指向实际输入原话，不能指向转换结果、自审结论或后序建议。按声明位置读取片段复核，正确hash不能补救错误定位。

<a id="business-5-4"></a>
### 5.4 支持结论与确认、处理状态分别交接

对每一受影响权项／特征，同时交接：权项及feature_id、当前说明书支持定位（未提供时明确缺失）、支持内容及不足、概括层级、合同四值中的支持结论、具体意见的confirmation_status、内容trust_status、独立处理进展、修改指令及其采用条件、来源和警示。独立处理进展为说明文字，不新增合同运行状态枚举，也不改变confirmation_status、警示或双状态原有值。

| 情形（仅规则示意） | T4支持结论及理由 | 确认状态与处理进展 | 下游可做的事 |
|---|---|---|---|
| 当前说明书明确记载槽约束滑动及转动约束，原技术来源可定位，但本轮未回复 | 充分；仅针对该已记载关系及相同概括层级 | pending；保留原source_fact，待本轮具体回复 | 可基于有来源内容提出条件性稿件／回退建议；关键关系未确认警示保留，不一律要求重复确认全部既有事实 |
| 说明书只写滑动，缺转动约束依据 | 部分；说明已支持和未支持的具体部分 | pending或partial按实际反馈判断；待补转动约束依据 | 分开已有来源部分和待核假设，不把整项充分或整项缺失 |
| 拟增加磁吸关系，当前累计快照无对应支持，反馈也只是“也许可行” | 缺失；对应支持定位记未提供 | pending；hypothesis_to_verify，待技术说明及支持材料 | 仅输出明确标记建议和追问，不纳入确认事实；不补造实施例 |
| 拟概括所有连接方式，当前仅披露特定槽配合且无其他方式依据 | 建议限缩；说明过宽部分与有来源回退边界 | 确认状态按真实命题另判，范围偏好不能代事实 | 给有来源范围内的限缩候选及理由，专业范围由人工决定 |

支持充分并不等于本轮沟通已确认；confirmed_fact也不等于当前说明书支持充分。支持结论、confirmation_status、trust_status、证据验证程度、处理进展及警示生命周期分别表达，不用一个状态覆盖其他维度。

技术来源可靠且当前说明书支持可定位时，允许依合同§4.11以有来源元特征形成从属回退建议。未获新的具体确认不自动废弃原source_fact；新增事实、来源冲突或关键关系未确认仍逐项警示。不得把本条用于自动正式提交批准。

<a id="business-6"></a>
## 6. 可执行修改指令

每项指令至少记录：`change_instruction_id`、关联`opinion_id`与技术ID、修改对象及定位、当前表述／缺失项、建议表述或操作、修改理由、来源依据、采用条件、确认状态、关联T表／权项／说明书／附图、联动影响及待处理事项。

1. 修改对象应明确到权项中的特征、说明书章节／段落、图号／标记或稳定ID；缺原稿定位时按ID和语义定位，并明确定位缺失，不能捏造段落号。
2. “保留、补充、纠正、删除、限缩、暂不采用、待确认”要指出具体内容。建议表述可供后序改写，但不提前编制完整正式权利要求或说明书。
3. 确认充分的指令标明可采用及依据；尚待确认的指令给建议文本、必要条件及不得当事实的限制；应排除内容进入不采用表。表名`confirmed_change_instructions`沿用合同，但不得将整表默认解释为已获发明人确认。
4. “优化权利要求”“完善说明书”“提高严谨性”不合格；必须写清哪项技术关系、哪个条件或何种范围需要怎样变动，以及为何变动。
5. 指令不等于已经修改正式稿；F-4-11负责正式权项和T6初版，F-4-12负责正式说明书、支持及图文一致性。涉及前序返工时仅给人工建议，不自动执行。
