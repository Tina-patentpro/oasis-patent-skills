# 专利制图—生成合同 V0.2.1

## 输入

| 内容 | 处理 |
|---|---|
| 绘图需求文本 | 必须有足够明确的主体与目的；用户可以直接用自然语言描述 |
| 参考材料 | 可选，记录实际读到的范围；明确是内容依据、风格参考还是目标图 |
| 尺寸/比例/数量/风格 | 只保留实际要求，未指定按工具支持作合理构图选择并区别于技术事实 |
| 编号/连接/顺序/方向 | 逐项保留，不因提示词压缩改变“或/且”、条件、反馈路径或结构数量 |

本合同来自既有图像工作流的语义整理和图形规划节点。不是专利技术事实补齐器，不把说明书撰写或检索任务混入图像生成。

## 绘图规划

建立 `visual_plan`：`image_type`、`requirement_coverage`、`prompt`、`figure_numbering_plan`、`view_description`、`numbering_list`或`flow_node_list`、`additional_figures_needed`、`assumptions`、`unresolved_items`。字段供内部核对/调用记录使用，用户只需得到所求图片与有用说明。

流程图：保留全部步骤、判断条件、肯定与否定分支、输入/输出和反馈。用清楚的步骤框、判断框和箭头；短中文标签可直接表达含义。流程图与机械实体分开。

结构图：保留部件、数量、连接、位置、动作、状态和指定视图。同一部件跨图编号一致，同一编号不指两个部件；未知的连接不得补成已知。明确数量的重复单元完整表达，总览承载整体数量、局部图承载细节。指定的剖面/局部图不能为简洁而省略。

技术专利图默认白底、清楚黑线、均匀线宽、留白，不增加装饰、商标和无依据结构。图号、部件名和长解释优先放图外；图内数字与引出线根据用户要求和表达需要安排。未指定时不强制凑视图数量、固定图1—图5或固定字数。图片生成存在文字/数量误差，实际结果须检查，未核项保留。

普通照片、产品图、海报等按其用途确定色彩、材质、光影和构图，不强加专利黑白线稿约束。用户明确的文字、风格、色彩和布局优先保留。

## 工具与结果

先发现当前会话可用图像生成/代码绘图能力；按工具实际支持的输入、尺寸、透明背景、参考图传递与输出规则调用。不写死旧提供方、不凭历史插件名声称有能力、不读取源YML凭据。工具缺失时只交规划和提示词，不制造图片URL或虚构调用。

工具成功后检查真实图片的需求覆盖；不能只根据成功状态或提示词判断画面对。返回实际可显示或可访问的产物，并保留来源、工具结果身份、未核项和必要修改记录。生成失败、超时未知、产物不可访问分别报告，不无限重试。

## 输出记录

| 字段 | 内容 |
|---|---|
| `status` | generated / generated_with_concerns / prompt_ready_tool_unavailable / needs_clarification / pending_verification / failed |
| `tool_status` / `tool_task_ref` / `artifact_status` / `verification_action` | 按[共用结果合同](result-contract.md)记录工具状态、实际任务身份、产物可访问性及核验动作 |
| `images` | 实际产物引用；未出图为空并说明原因 |
| `visual_plan` | 需求覆盖及生成提示词/图外说明 |
| `checked_requirements` | 实际查看后核过的数量、关系、标签、视图和风格 |
| `unverified_or_conflicting` | 实际未核、冲突及仍需用户确认的项 |

这些是Skill调用的记录字段，不给普通用户增加填表或理解接口的负担。图像编辑须传入实际目标图，不从本合同默认为另造新图。
