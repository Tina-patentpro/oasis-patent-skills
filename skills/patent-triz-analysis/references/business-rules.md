### 1.1 生成物与成功目标〔R01〕

`triz_analysis_report`主要用于帮助使用者选择一个或几个值得进一步探索的研发方向。它把实际收到的技术背景转化为关键问题、问题模型、资源、候选解决路径及有条件的方向建议。只读这一文件，应能理解：对象如何工作、关键不足为何发生、为什么优先解决这些问题、TRIZ线索怎样转化为候选、各候选怎样回应原问题/矛盾、建议探索什么及为什么、先验证什么，以及哪些证据会改变建议。概要检索与累计交接仍是必要支持，不替代研发判断。

成功不取决于字数、表格数、工具名、原理编号或候选数量，而在于“关键问题选择—TRIZ求解线索—具体技术路径—候选回查—方向比较—有条件建议—首个验证决策”可追溯。证据不足以支持选择时，明确说明暂不排序，并指出决定性缺口及优先验证事项，同样可以符合报告要求；不得为交付结论强选方向。报告是否生成完成、技术路径是否解释完整、机理推导是否有依据、效果是否已有验证，以及是否值得投入研发，是不同层面的判断，不得用“可实施”一词混为一谈。

### 1.2 职责与边界〔R01、R02〕

- 承接Flow-1-1背景，但不重做全领域研究；必要补充只服务当前问题，外部技术断言按§2.1核查。
- 分析并校订问题、原因、约束、矛盾及资源，把方法启发转为结构、关系、步骤、算法、工艺或控制手段。
- 分开表达原有方案、上游已有技术路线和本节点新候选；材料中有记载不等于已经实测，模型设想不是用户事实。
- 必须在实际目标和约束下比较候选并提出研发探索建议，或明确为何暂不能选择及下一判断动作。F-1-2给出当前技术依据下的研发建议，不等于最终立项、采购或投入承诺；不替代Flow-1-3概要检索，也不冻结由Flow-1-4结合检索风险与申请类型选定、拟纳入交底书的主备方案。后续证据可以改变建议；不对新颖性、创造性、最接近现有技术或保护范围作最终判断。
- 不要求每个早期候选已有实验验证，也不允许以“尚需验证”为理由省略能由现有材料完成的分析。
- 不撰写正式申请文件，不处理权属、优先权或其他程序性事项；这些边界不必复制为报告中的通用免责段。

### 1.5 系统、问题、根因与矛盾〔R05〕

**先理解作用路径，再建立问题模型。** 用最小必要表达交代对象/系统边界、主要功能、关键交互、正常工作路径、典型工况及不足发生位置。不要复制背景全文来替代分析，也不要求完整九屏幕、功能矩阵或固定形式图。

机械侧重受载、运动、约束及连接；控制/软件侧重数据、触发、状态、模块和时序；材料/工艺侧重组成、步骤、条件和状态变化。TRIZ理论的物理概念与这些领域的项目表达并不当然等价，迁移使用须说明映射与限制，不把数据强称为物质，也不把算法强称为物理场。

| 分析单元 | 最低解释与判据 |
|---|---|
| 技术问题 | 对象/场景—现象—发生条件—功能影响—改进目标；关联`tp_id`与来源 |
| 根因链 | 区分现象、直接原因、进一步原因及可干预环节；每个关键因果连接有材料依据、机理解释或待验证标识 |
| 问题优先级 | 按功能影响、约束、可干预性和用户重点说明，不以问题数量或抽象评分代替判断 |
| 技术矛盾 | 某项改变使一个参数改善，却经可说明机制使另一个参数恶化；两个参数及其变化、共同条件及因果联系清楚 |
| 物理矛盾 | 同一对象的同一参数需要满足相反要求；分别说明要求为何必要、作用时间/位置/状态或其他条件 |

**关键问题是为当前研发目标选定的待解问题，不是最长原因链或表中第一行。** 根据功能影响、根因/可干预性、硬约束和用户重点说明为什么优先处理；关联`tp_id`，保留暂缓问题及影响。区分用户目标/偏好、必须满足的技术约束与本节点推导的优先级；目标或工况未明确时列出会改变路线判断的缺口，可给限定场景的条件建议，不暗造预算、期限或性能目标。

根因链不固定“追问几次”，不把同义复述当深入，也不能因一条链得到解释就排除其他有据原因。未经验证的链不得称唯一根因。两个并列目标不自动构成技术矛盾；信息缺失不构成物理矛盾；既有条件已足以实现不同要求时，说明是否仍有待解决的冲突，不能直接宣称矛盾已消除。

两类矛盾均须经过判断，但不要求每个问题都产生两类条目。无矛盾、无法建立或证据不足时写明理由与分析边界，不空填矩阵，不将问题简化为“效率与成本”式的万能矛盾。工程参数映射须有具体含义与理由；编号不能证明矛盾成立。

<a id="business-1-6"></a>
### 1.6 资源、目标与方法选择〔R06〕

资源分析说明：资源的来源、所在位置/时间或可用状态、拟利用方式、限制及新增代价。可考虑现有组成、环境、空间、时间、能量、信息或相关能力，但不要求填满所有类别。模型提议引入的新部件、信号或能力应列为新增条件，不冒充现有资源。

理想目标用于约束方向，不是实测结果或性能承诺。需要时用理想最终结果等表达希望保留的功能、希望消除的不足和不愿新增的代价；不能用理想口号跳过技术路径。

区分问题识别工具与解题工具：功能分析、因果链等帮助定位关键问题，不能仅列这些工具就声称产生了TRIZ解决方案。按已建立的问题模型选择解题工具，说明适用理由、实际获得的线索和技术转化；不要求全套工具打卡或强制执行完整ARIZ。以下为适用路线举例，不是全部工具清单或强制流程，具体采用时核查出处和版本：

| 问题模型 | 可采用的解题路线 | 最低可追溯内容 |
|---|---|---|
| 工程/技术矛盾 | 矛盾矩阵等导向发明原理 | 具体改善/恶化参数及动作、采用矩阵时的参数映射/版本/返回线索、具体转化；矩阵建议不等于可行性或优先级证明 |
| 物理矛盾 | 分离方法或其他有据求解工具 | 同参数的两项必要要求、各自条件、选择的分离/处理线索、满足两项要求的机制与适用边界 |
| 物—场问题模型 | 有据标准解等 | 与关键问题有关的物质、场及不足/有害作用，所选解题线索和实现方式；不能把任意软件关系硬称为物理场 |
| 功能问题模型 | 功能导向搜索、科学效应等 | 功能载体/对象/目标作用、实际搜索或效应线索、向当前系统迁移所需条件；未检索不得编造已检得技术 |

对每条声称由TRIZ产生的候选，记录“所选关键问题→问题模型→工具及线索→具体技术转化”，可用自然语言并关联同文件定位，不强制新增图、编号或JSON字段。外部方法名称、参数、矩阵版本和编号须核查可靠出处，找不到依据则保留自然语言分析并标注为未核查，不冒称标准匹配。一般工程改进、既有路线或非TRIZ设想可以保留并比较，但如实标注来源和贡献，不事后贴原理名称伪称TRIZ推导；TRIZ路线未形成候选时说明实际尝试、原因和下一动作。

### 1.7 方案卡、完整路径与技术要素〔R07〕

`solution_cards`在同一主文件内承载候选方案，不规定固定数量。每个候选以稳定`solution_id`关联问题，说明：

1. 来源和相对有效基线的具体变化：新增、删除、改变或保留什么；
2. 来源路线及方法贡献；声称TRIZ推导时按§1.6贯通关键问题、模型、工具线索和技术转化，不只粘贴原理名称；
3. 技术实体/载体、关键关系、手段和动作过程；
4. 触发或初始条件、状态/时序、必要配合与结果；按领域适用，不强凑机械动作；
5. 手段如何实现功能并产生局部效果和整体效果；
6. 成立条件、关键参数的作用、限制、代价及新增失效风险；
7. 事实、推导、待验证假设、缺口与验证需求；
8. 原问题/原矛盾回查及对研发建议的影响。

**完整技术路径判据：** 读者能连贯说明“谁/什么，在什么条件下，以哪些关系和动作作用于什么，怎样得到目标功能/效果”，且关键环节不依靠空泛愿望来衔接。删除构件时说明原必要功能由谁承担；添加算法时说明输入、输出、触发、状态和关联对象，不以“智能优化”代替机制。

这只是概念路径解释完整，不等于全部工程细节已确定或效果已证实。关键接口、资源或条件尚不明确时，说明缺口，不能编造尺寸、牌号、阈值或结构来填满表格。路径不足的候选可保留供分析，但不得宣称已完整、可直接撰写或已可实施。

按宏特征—元特征—元实体/元关系/元手段/元功能/元效果拆解。元特征是语义完整的技术单元，不应拆成单个名词；保留相互配合与组合关系，不能拆散后误称每项独立取得整体效果。实体/手段/功能/效果不可互相换名复制。

**候选回查：** 沿“原问题/矛盾→干预机制→原两参数或相反要求如何处理→新增代价/失效/矛盾→当前判断及验证”逐卡核查，关联原`tp_id`与矛盾定位。对于技术矛盾，说明拟改善参数是否可能得到改善、原恶化参数如何避免恶化；对于物理矛盾，说明两项要求在各自必要条件下怎样满足，以及条件重叠时是否仍冲突。区分拟消除、缓解、转移、折中、未处理或证据不足，并说明依据强度；未经验证不得称已消除。牺牲另一要求、把问题移给其他构件/工况，均不能仅因主指标改善就称已消除矛盾。原矛盾未成立时回查原功能/不足，不强造矛盾；新问题影响可接受性时纳入方向比较和警示。

**实质方向与组合：** 不同名称、措辞或无作用差异的细节不构成多个实质方向。按机理、关键关系、实现路径和条件识别重复与变体；同一路径变体可归组，实质不同的路径不得强行合并。用归入该方向的各候选方案的`solution_id`说明归组、旧ID映射及理由，不要求新增方向ID。拟多选时，说明所选方向之间的替代探索、互补组合、前后依赖或条件不兼容关系，以及各自要验证的假设、推进顺序和组合风险；这些关系可并存但不得相互矛盾。替代方向可并行验证，不等于可拼成同一系统；互补需解释接口/作用配合；依赖需标明前置条件；不兼容者说明分支条件，不能推荐为可同时实施的整体。只展开会影响选择的关系，不建设穷尽式两两矩阵。

**方向比较与有条件建议：** 先明确共同目标、工况、有效基线和硬约束，再用相同含义的比较项目评价各实质方向：

| 比较项目 | 必须说明的判断依据 |
|---|---|
| 问题价值 | 为什么值得解决、影响什么功能/工况、与研发目标的关系；不能只重复问题标题 |
| 潜在技术收益 | 相对有效基线可能改善什么、机制与证据支持到哪里、是否以其他必要功能退化换取；不把期望当实测 |
| 决定性障碍 | 路径/机理的关键未知、约束冲突、新矛盾和失效风险；哪些会改变选择 |
| 资源与投入条件 | 现有与新增部件、能力、接口、材料或设施及获取条件；金额/周期未知则明示未知 |
| 验证难度 | 决定性假设如何检验、所需条件与相对负担、哪些证据暂不可得 |
| 当前建议 | 优先探索、暂缓或暂不推荐的理由、成立条件、首个判断动作和改变建议的证据；用文字表达，不新增业务状态枚举 |

比较结论逐项引用候选、来源和验证定位，可通过候选方案表的补充列或同文件中的比较段呈现，不强制增加表格数量。目标/工况不同的方向不能直接假设同一排名；明确分支情景及推荐变化。未满足硬约束或其满足情况尚未知的方向，不得推荐为可直接实施，可建议限定的机理验证并说明条件。仅一个方向时与基线比较，没有完整方向时给问题/机理核查优先级。证据不足以排序时指出具体缺口、影响和先获取何种证据，不强选“第一名”。不设固定权重或总分，不编造预算、期限、收益和数值门槛；有真实约束才使用，并保留来源。推荐或暂不推荐均不是永久淘汰或已证实最优，不删除相关方向的有效技术内容。

### 1.8 效果、验证与成熟度〔R08〕

每个关键效果关联问题和具体特征/组合，说明作用机理、成立条件、指标或观察方式、证据状态。区分用户期望、文献记载、仿真/计算、用户实测、本节点推导及模型假设；材料中的直接记载不自动等同于相关效果已经过实验验证。

验证需求不是“建议做实验”的通用句，至少交代：待验证主张、可采用的方法、工况及比较基线、观察量与预期方向、会否定或限制主张的结果。无合理数值依据时用定性判据，不编造阈值；无需每个早期候选都有完整实验规程，也不以模型置信度代替验证。

**首个决定性验证动作：** 对拟推荐方向，将最可能改变选择的未知项与`solution_id`、问题/效果及建议关联，说明“决定性未知→最小可行实验/计算/原型或必要取证→所需资源及工况/比较基线→观察与否定判据→继续/调整/暂缓触发条件”。解释为何先做它，以及它能排除什么，不以堆列试验代替优先判断。动作尚不可执行时列明前置资源/资料和获取次序，不编造已有设施或已完成验证；方法不足以分辨关键假设时如实说明。暂无可推荐方向时，给出最先澄清关键问题、条件或机理的动作及其对后续选择的影响。这是验证建议，不是自动试验、付费调用或立项授权。

成熟度采用明确文字分别描述，不新增合同枚举：路径是否完整、机理支持到何处、效果有没有验证、哪些环节待确认。分析充分但证据不足的候选与无依据宣称成熟的候选必须区别评价。
