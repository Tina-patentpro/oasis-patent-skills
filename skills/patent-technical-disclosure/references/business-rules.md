# 授权技术条款摘编

OasisIntWrite，2026-11-07。以下是获授权自编规则的具名技术条款，未复制历史治理、收据、案例或评价答案。修改：本包独立合同与核心规则规定普通材料输入、身份、保存、状态和累计边界；条款里的前序品牌只在明确链式任务适用，不能成为独立前置。章节号用于精确核对，缺失的输入/运行/治理条款由本包合同替代，不要求回读源项目。技术来源、原草案效力及未验证边界见sources.json。

<a id="business-1-1"></a>
### 1.1 生成物、双读者与成功目标〔R01〕

`disclosure`是把Flow-1-4实际传入的选定技术方案、累计内容和本次用户补充整理为**正式技术交底书与完整累计交接文件**。它为用户确认、F-2-6权利要求初稿及后续说明书撰写提供技术依据，不是已经审定的权利要求书、申请说明书或授权保证。

双读者分别是：能够核对自身研发内容、但不要求懂专利语言的用户；需要可复用技术依据的撰写者或下游Agent。前者应能回答“问题是什么、如何做、为什么有效、哪些说法确有依据、我要确认什么”；后者应能定位实体、关系、步骤、条件、效果、来源及稳定ID。两者必须读取同一份文件中的同一有效技术基线。

本标准主要约束LLM/Agent，不要求普通用户阅读本标准、理解评分、填写T表或维护ID。生成端应组织好这些技术与追溯信息，让用户阅读交底正文、核对具体确认问题；不能把本应由撰写者完成的专业整理工作转嫁给用户。

成功不取决于篇幅、术语密度、表格数量或把全部空白填满。应尽可能形成完整实施路径；材料不支持时，完整地说明已知内容、决定性缺口及最小补充需求，而不是制造形式上的完整。形式齐备、事实可信、技术可实施性与用户确认状态分别核查，不互相推导。

主线沿用实际上游的主方案及申请类型；备选按实际有效内容处理。没有主方案、多组推荐尚未定主线或主线冲突时，明确待用户选择，逐组整理已有内容，不擅自挑赢家、合并成一个发明或补造备选。源材料支持的主方案、备选及适用条件不能因追求简洁而丢失。

<a id="business-1-4"></a>
### 1.4 正式技术正文与完整性〔R04〕

交底正文使用准确、克制的书面语言，明确主体与对象，不用营销词、口号、无依据绝对化表述或整段权利要求句式代替技术解释。名称、单位、指代、方案版本、图号和步骤编号前后一致。对重复段落可合并表达，但不得合并不同方案的条件或掩盖实质冲突。

在固定`## 核心结果`之内以三级标题组织，覆盖以下内容；缺项写明已知部分、为何缺、影响与补充动作，不保留没有解释的空表、TBD或“按常规实现”：

1. 技术名称、领域、对象及使用场景；
2. 背景技术、现有不足、技术问题及目标，区分源记载与分析；
3. 主方案整体组成、宏特征、元实体、元关系、元手段、元功能、元效果及相互作用；
4. 技术手段如何解决问题、整体效果、成立条件与证据限制；
5. 至少一条具体实施路径，关键材料、参数、步骤、控制及失败边界；
6. 实际支持的备选、替代和优选实施方式，说明可替换对象、条件及不适用边界；
7. 附图说明/计划、图号、标记及图文映射；
8. 冻结版T1/T2/T3、方案—要素—效果矩阵、术语表、来源登记及模型补齐登记。

必要特征、可替代特征、优选特征和仅实施例特征逐项说明依据，未知记待确认。F-1-5提供撰写依据，不把候选必要性判断冒称最终独权或保护范围；也不提前生产完整权利要求、T4/T5/T6来代替后续节点。

<a id="business-1-5"></a>
### 1.5 实施路径与技术链闭合〔R05〕

主方案须按“对象/输入与初始条件→必要实体或步骤→连接/交互/转换/时序→控制或关键条件→输出/结果→与目标效果的关系”说明至少一条连贯路径。指出哪个主体执行、如何执行、先后与触发条件、结果如何被使用或验证。备选只在确有技术来源时给出完整或受限路径及切换条件。

“模块用于提高精度”“通过优化实现”等仅说明功能，不算实现手段。不能用部件名单代替连接关系、流程框代替处理逻辑、效果目标代替成立机制。对决定性环节说明具体内容或明确技术缺口；一般常识仅在可说明适用依据、不掩盖创新关键环节时作为背景解释，模型增加的实现仍须登记。

区分源支持路径、合理推导路径、待验证条件性路径；路径写得连贯不证明工程已实施或实验成功。如果至少一条可实施路径仍不能建立，保留已有内容并突出决定性缺口，使用不建议直接申请的交付边界，不以虚构环节凑完整。

<a id="business-1-6"></a>
### 1.6 领域适配与申请类型〔R06〕

只写对实际方案适用且有依据的细节，不强迫各领域套同一结构：

| 领域/对象 | 重点核对，不足则受限 |
|---|---|
| 机械、电气、结构 | 部件位置、连接、运动/受力/电流路径、接口、装配与工作状态；明确图证据与推导区别 |
| 软件、控制、通信 | 技术对象、数据含义、输入输出、处理/计算、状态与时序、控制触发、异常分支、部署关系及技术效果；不能只有业务结果或模块名称 |
| AI模型 | 适用时说明必要模块/连接、训练或使用步骤、必要参数、数据与场景关系；不得为“完整”虚构架构、数据集或训练成绩 |
| 材料、化学、工艺 | 组成/结构、原料、制备或加工顺序、决定性条件、测定方法与效果；推导结构/配方/合成路线须标假设，不保证可制备或药效 |

承接`invention`、`utility_model`或`undetermined`。类型未定保留待确认；纯方法或算法不能靠改名“模块”、虚构连接来变成已支持的产品形状/构造方案。产品形状、构造或其结合按实际技术来源检查，不要求每种产品同时具有独立形状和构造改进。类型适配、技术实现和可授权性不是同一结论。

<a id="business-1-7"></a>
### 1.7 参数、效果、公式与证据〔R07〕

每项效果对应`te_id`、技术问题、特征或组合、作用机理、成立条件、边界、指标/测量方法和证据状态。区分元功能、局部效果与整体效果；不把“能完成动作”直接提升成整体性能改善。对定量比较记录基准、条件、方法、单位与数据范围；没有可信数据不编造提升比例、精度或寿命。

关键参数说明含义、单位、作用、来源和适用范围；区间、端点、容差、配比及参数耦合仅在有依据范围内使用，不由单点实验外推普适范围。不要求所有交底都有定量结果；确为实施必要而缺失的参数要成为具体待确认项，不用任意数值填补。

涉及公式时解释符号、量纲、条件和参数关系，核对正文、计算、表和图是否一致；来源不足的推导公式或数值示例标记为模型补齐/假设，不当测量结果。无适用公式时说明不适用，不为凑格式创造公式。

T3以实际有效上游状态为基线。无有效增量时继承；有效新证据仅在支持的对象、特征、条件范围内修订；明确撤回/替换证据转历史并按剩余证据调整当前项；冲突未决保留双方与受限判断。记录旧/当前值、来源/哈希/定位、核查范围与理由；其他效果不连带升级。文件自称“验证成功”、用户认可表述或模型认为合理，不自动证明本节点独立验证或全部效果已验证。

<a id="business-1-8"></a>
### 1.8 附图与图文一致性〔R08〕

实际有图时逐图登记图号、名称、来源/页位、标记、对应实体/特征和关系，核对正文、路径、T2及图中连接/位置/时序。图号与部件标记有清楚映射，不得一号多义或因换名丢失身份。关键线条或标记不可辨识时列出具体对象与影响，不臆造隐藏结构。

无图仍给出有依据的附图计划：拟说明何种结构、流程或关系，需要哪些信息，哪些只是建议且尚未制作。计划、示意解释和已提供实际附图明确区分；没有图像输出不得声称附图已完成或渲染成功。图文冲突保留来源与版本并待确认，不自动选一版。正文应直接描述核心技术关系，不能只写“见图”让下游无法理解。

<a id="business-1-11"></a>
### 1.11 非专利用户理解与准确确认〔R11〕

这是独立关键要求，不是完成专业正文后可有可无的润色。默认用户了解自己的技术，但不要求懂“独权必要、元关系、创造性、充分公开”等专利词。先用主体、动作、对象和条件解释技术，再在必要位置给标准术语；首次出现的缩略词/领域术语给简短准确解释，同一概念一名到底。稳定ID放在括号或表格供追溯，不用ID串代替可读叙述。

“用户确认摘要—完整技术正文—具体确认清单”三层均在同一主文件内；不维护另一份脱离正式文件的事实版本。摘要和通俗说明可以减少阅读负担，不能删除“不一定、仅在某条件、尚未验证”等实质边界。类比只用于解释，明确不是新增结构或证据；不以口语化改写歪曲逻辑。

每项待确认问题至少写明：对应正文位置及`warning_id`或内容ID；当前具体说法及来源/假设；用户要核对的一个事实或一组不可分条件；为何影响技术或下游；需要的回复/文件/数据。先列决定性缺口，其后一般纠正。避免“是否确认全文”“是否具有创造性”等要求用户替代专业判断的笼统或诱导问题；允许“准确、需改为……、不确定、尚无数据”等实际回复，不预填用户结论。

将确认分为表达理解、具体技术事实、效果/验证材料三类；用户说“看懂”“总体同意”、接受风险或未回复，不等于所有模型内容转为`confirmed_fact`、效果已实测或警示全关闭。具体确认由明确返回的实际内容、位置、范围及来源支持；数据验证状态另核查。回复内容用相应技术/附图/数据文本通道，处理指令用`user_input`；本轮不设计新输入ID或自动回流机制。

举例性的提问方式：“第X节说部件A在条件C下与B保持连接。这是您实际的设计吗？如有差异，请说明连接位置与动作顺序。”这里只演示问法，不向真实交底加入A/B/C部件或假设。缺少专业词不等于缺少严谨性，用户觉得易读也不证明能实施。
