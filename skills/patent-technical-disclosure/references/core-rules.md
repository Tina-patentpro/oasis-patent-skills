# 技术交底的业务规则

本文件由OasisIntWrite根据自有F-1-5规则V0.1.2及本次独立合同改编（2026-11-07）；独立模式的输入和交接按本包合同，原规则效力不因本改编提升。

## 问题、方案与实施链

技术交底服务于技术确认和后续撰写，不是权利要求书、法定提交说明书或授权保证。默认读者懂自己的研发，不要求懂专利术语；解释技术关系，不用ID串、营销词或权项长句代替正文。

分别整理实际主方案与有据备选。没有已选主线时保留各组及选择问题，不合并互斥技术方案。申请类型只按实际材料承接；未定保留undetermined。不能通过给算法改名“模块”或虚构形状连接来制造产品构造依据。

按“对象与初始条件→实体／步骤→连接交互／转换／时序→触发和关键条件→输出→效果关系”组织至少一条源支持路径。部件清单、模块功能或“按常规实现”不算完整实施手段；决定性连接、异常行为、制备条件等缺失时，逐处写出缺口与影响。

机械／电气核位置、连接、运动／电流路径、接口和装配状态；软件／控制核技术对象、数据含义、处理步骤、部署、状态、触发和异常；AI方案只在有源时写必要架构／连接、训练或使用步骤及数据场景关系；材料／工艺核组成、原料、步骤、决定条件与测定方法。不为套模板发明结构、训练成绩、配方或药效。

## 交底正文

核心结果至少写清：技术名称／领域／场景；背景与问题；方案组成和相互作用；手段解决问题的机理与条件；实施路径和关键参数；有据替代及不适用边界；实际附图或未制作的计划；术语、T1—T3、来源、模型补齐与具体确认问题。缺项写已知部分、缺口、影响和最小补充动作，不保留无解释空表。

必要特征候选、优选、可替代及仅实施例特征分别解释依据；它们不是已审定独权或最终范围。不要提前生产完整权利要求或T4/T5/T6；若实际输入已有这些内容，则保留其身份和未验状态，不因本节点职责删除。

T1保留tp_id、对象／场景、缺陷、原因／机理、目标、指标／测量方法和来源状态。
T2保留solution_id／macro_id／feature_id、关联tp_id、元实体、元关系、元手段、元功能、元效果、必要性与来源状态。
T3保留te_id、关联tp_id、特征／组合、机理、条件／边界、指标／测量方法和证据状态。表由执行者生成，未知值附解释；冻结只是本次有效版本身份，不等于事实确认。

## 参数、效果与附图

参数解释含义、单位、作用、来源及适用范围；区间、端点、容差及耦合关系不能从单点擅自外推。实施所必需的参数缺失要具体追问，不任填数值。公式解释符号、量纲与条件；不适用则不硬造。

效果对应问题、特征或组合、机理、条件、边界及证据。元功能、局部作用与整体改善分开；定量比较必须有对照、条件、方法、单位与数据范围。没有实验或可信计算时只记预期，不编百分比；逻辑上减少一次启动不等于已证减少现实误启动，也要保留响应代价等未验证问题。

有图时实际查看并逐图核图号、标记、实体和连接／方向／时序；不可辨识的具体对象列未核，不猜隐藏结构。图文冲突保留两方来源。无图时给有依据的附图计划，明确尚未制作；正文仍直接说明核心关系，不能只写“见图”。

## 来源与易于确认

按独立合同保留每项事实／推导／假设／确认的来源。模型补齐至少注明依据、假设、信心、受影响位置和待确认状态；不把外部文献结构或效果迁成用户方案。新内容保留新身份，实质修改保留旧值、新值、来源与原因，不静默改号或恢复撤销内容。

同一技术基线生成确认摘要、完整正文和逐项问题。每个问题指向正文／内容ID及警示，说明当前具体说法、来源／假设、需要核对的事实或不可分条件、为何影响技术及所需回复／材料。允许准确、需改、不确定、无数据等真实回答，不预填结论，不问“是否确认全文”来获得批量确认。

摘要和通俗解释不能删去条件、增加事实或升级证据。看懂、总体同意、接受风险和未回复不确认所有参数或模型推论；效果验证与表达认可单独记录。

## 自检与用途

逐项核问题—必要关系—手段—机理—效果—条件是否有源，正文／表／图是否一致，主备及人工改动是否保留。关键关系缺失、路径不完整、图文冲突或参数单位异常必须写具体影响，使用not_recommended_for_filing，仍可交讨论稿。程序只能核身份、格式和计算，不能替代技术判断、专业审阅或用户确认。
