# 授权技术条款摘编

OasisIntWrite，2026-11-07。以下是获授权自编规则的具名技术条款，未复制历史治理、收据、案例或评价答案。修改：本包独立合同与核心规则规定普通材料输入、身份、保存、状态和累计边界；条款里的前序品牌只在明确链式任务适用，不能成为独立前置。章节号用于精确核对，缺失的输入/运行/治理条款由本包合同替代，不要求回读源项目。技术来源、原草案效力及未验证边界见sources.json。

<a id="business-1-1"></a>
### 1.1 用途、读者和成功目标〔R01〕

`patent_report`是对当前正式权利要求、说明书、摘要和附图进行技术实体内容终检的报告，同时是交给Flow-6-14的完整累计技术基线。读者是用户、专利专业人员及实际消费该文件的后序节点。

有用的终检应让读者知道：检查了哪个版本、哪些权项和特征；结论基于哪些原文；最影响申请质量的缺陷或证据缺口是什么；可能受到什么技术质疑；如何纠正、由谁确认、建议回到哪个节点；哪些风险仍未解决。不能仅列“符合要求”“建议完善实施例”等泛化结论。

检查围绕技术问题TP—技术方案TS—必要元实体/元关系/元手段—作用机理—技术效果TE—权项—说明书支持展开。正式稿终检不能套用初稿“方向可讨论即合格”的目标，但真实材料不足时仍交付受限报告，不虚构内容使其看似满足正式稿要求。

<a id="business-1-2"></a>
### 1.2 范围与人机责任〔R02〕

本节点覆盖中国发明和实用新型申请文件的技术实体内容及相应技术审查预演，不处理权属、优先权手续、首次公开调查、费用、期限或电子提交。技术客体、实际可制造/可使用等与当前方案直接有关的问题可以指出；不把本节点扩展为全面法律合规认证。

- LLM负责技术语义、证据解释、必要特征、支持边界、技术效果、模拟质疑和提交使用建议；代码只可观察、校验和组装可机械核验的字段，不以关键词、分数或计数裁定专业结论。
- 用户或专利专业人员负责事实确认、保护范围选择、正式文本修改、返工和最终提交决定；审查员的审查判断不能由工作流冒充。
- 不自动改写当前正式文本，不自动调用前序节点，不自动重跑、不替换提交文件、不承诺授权概率。发现缺陷后仍生成终检报告。
- 不指定模型、供应商、节点数、价格、最低字数、固定实施例数或自动执行方式；成本偏好不能造成未披露的抽样漏检。

<a id="business-1-6"></a>
### 1.6 逐权项技术闭环与形式表达〔R06〕

覆盖当前全部独权及其从权，不抽样代替逐项检查。每项独权至少定位技术对象/场景、关联TP、必要特征组合、实体/关系/手段、实现路径、对应TE及证据。检查必要实体是否有连接、交互、顺序、控制或条件等关系使其构成方案；不能因几个部件或步骤名称均出现就判闭合。

从权检查引用对象、引用层级、限定是否真实附加且与被引用方案兼容，以及该限定的技术作用、支持与回退价值。不能强制每项从权独立解决全新问题或都产生协同效果；有依据的实施优选/限缩仍可能有价值，纯重复或矛盾限定需指出。

检查权项的对象、术语、指代、引用、单位及必要技术关系是否可辨，是否存在影响范围理解的歧义或非必要重复。简要性不以字数裁定，清楚性不以是否套用固定措辞裁定。发现问题须引用具体文字并说明可能的不同理解。

### 1.7 公开、支持、概括、效果与单一性〔R07〕

| 检查面 | 必须形成的实质记录 |
|---|---|
| 公开与可实施性 | 至少一条已有材料支持的完整实现路径，关键条件/步骤/参数/关系是否足够；不能用“常规手段”遮蔽决定性缺口 |
| 逐特征支持 | 权项号/特征序号/`feature_id`→说明书段落、实施例、图或表→技术作用→支持结论；写明充分、部分、缺失或建议限缩的理由 |
| 概括边界 | 上位概括、并列选择、功能限定、参数范围实际涵盖哪些方式，依据能否覆盖；区别文字一致与实质支持 |
| 技术效果 | 特征/组合→机理→条件→指标或验证方式→现有证据及强度；不把设想、仿真或模拟数据冒充实测 |
| 单一性联系 | 标出多独权或同一权项中并列方案相同或相应的特定技术特征、共同贡献依据及证据限制；仅同一用途/部件名称相同不自动证明单一性 |

缺少实验数据不自动等于不可实施、无支持或无创造性；判断该效果或范围是否需要额外证据，并说明现有机理/记载能支持到什么程度。反之，已有数据不自动证明整段概括范围，也不能把单个实施例数值外推为确认的全范围效果。

按实际技术领域展开：机械重结构和关系，软件/控制重输入输出、步骤和技术作用，材料/化学重组成、条件和效果边界；不能要求每个领域填齐所有类别，更不能用这些侧重点缩减默认检查范围。

<a id="business-1-8"></a>
### 1.8 术语、摘要、附图与来源一致性〔R08〕

比较同一实体/步骤/参数在权项、说明书、摘要、术语表、T表和附图中的含义、关系及标号，核对图文能否共同支撑方案。摘要不能新增正文未支持的技术方案或效果；摘要中的内容也不能自动充当权项支持或修改依据。

区别“没有图”“图像未能读取”“看见图但与文字冲突”；只有文字说明时只检查可读文字，不声称图像核验完成。实用新型的形状/构造图示检查有其申请类型要求，不能套用“发明不总需附图”的解释消除缺图风险；申请类型不明时作条件判断。[实施细则第二十至二十六条](https://www.cnipa.gov.cn/art/2023/12/21/art_3317_189352.html)

来源事实`source_fact`、明确确认事实`confirmed_fact`、合理推导`reasoned_inference`、待验证假设`hypothesis_to_verify`和`excluded_from_formal_text`保留区分。来源定位应确切到输入、权项、段落、页、图或文本块，不用模型推导、前序结论或本报告自述冒充原始记载。

<a id="business-1-9"></a>
### 1.9 T5、新颖性与创造性技术预演〔R09〕

每项独权均给出T5检查结果和最接近现有技术候选建议；继承T5不等于本轮已经核验。说明本次实际能读取的文献证据及不能读取的部分，候选接近理由、特征比对、区别组合、对应效果、实际技术问题、技术启示与结论强度均应有依据。

新颖性风险分别对应每一件文献的披露范围，不把多篇各自披露拼接成“单篇完整覆盖”。同一文献不同位置的内容也须核对是否属于相互联系的同一技术方案，不任意拼接互斥或无关联实施例；不能反过来要求所有特征必须在同一段落才算披露。创造性预演对权项限定的整体方案分析，不把相互作用组合任意拆散；讨论结合动机、实现路径、合理效果预期与技术障碍，不能以“可以拼起来”代替技术启示。实际技术问题不能直接包含区别特征或其暗示。[单独对比原则的官方案例说明](https://ipc.court.gov.cn/zh-cn/news/view-4898.html)

发明与实用新型的适用判断不同，未知类型不默认为发明。提出候选建议与技术风险，不宣告最终最接近现有技术、完整检索、已证明授权或最终法律结论。[专利法第二十二条](https://www.cnipa.gov.cn/art/2020/11/23/art_524_171347.html)

2025年修改决定强调发明创造性分析以权项整体方案为对象，并关注作出技术贡献的特征是否进入权项。本终检据此检查“说明书中论证的贡献是否实际受权项限定”，但不因增加无关限定就推定创造性增强。[修改决定第六项，2026年1月1日起施行](https://www.cnipa.gov.cn/art/2025/11/14/art_99_202568.html)

只有摘要、前序结论、节选或未确认全文时，限定至已读片段；不宣称复核全文。文献时间资格或关键证据不明时标记未核验，不自行推断它已经是法律现有技术；本节点不因此新增首次公开/优先权调查。外部检索或调取全文须另有授权，不能借终检默认启动。

### 1.10 修改依据、模型补齐与建议〔R10〕

T6逐项保留修改对象、修改前/后精确文字或范围、原申请依据、技术理由、超范围检查与处理建议。核验实际可用材料能否支持该修改，不能把上游“已确认”标签或正式稿名称等同原始提交依据。

提交前的技术来源追溯与提交后的原申请公开范围判断分开：若没有原始提交文本，记录无法核验该层面，不把交底书、后补材料或模型补齐当成已提交原文。不得为填满T6回读旧文件；相关原文未在当前输入中可读时列缺口。[专利法第三十三条](https://www.cnipa.gov.cn/art/2020/11/23/art_524_171347.html)

模型可补齐缺失报告章节、分析过程或基于已有材料的解释，但不能补造证据、图像、实验结果、正式文本或已确认技术事实。每项补齐记录`content_origin=model_completed`、`completion_basis`、`assumptions`、`confidence`、`affected_section`和`human_confirmation_status`。

纠正建议列可核查动作：对应问题/权项/特征、已有依据、拟补充或限缩内容、所需材料/确认、范围或效果影响、建议返工节点及预期改善。不得仅说“加强创造性”；没有依据的技术补充只能列待验证方向或不采用建议，不能作为可直接提交的修复。修改后的完整替换稿不是本节点默认交付物。

### 1.11 问题清单与模拟质疑〔R11〕

每个问题至少记录以下字段；表格或紧凑分项均可，不能删掉实质内容：

| 字段 | 要求 |
|---|---|
| `issue_id`、检查类别 | 本轮稳定编号和问题归属；关联已有警示时保留原`warning_id` |
| 权项/特征/受影响内容 | 独权、从权、段落、图、T表或累计内容的准确位置 |
| 待检原文定位与证据 | 实收版本、输入ID、实际片段定位、来源哈希及已读证据范围 |
| 判断、理由与证据边界 | 已证实缺陷、待核验风险或本次未发现问题；给出推理，不把缺证直接写成否定事实 |
| 影响级别及理由 | 重大、一般或改进建议；依据实际对实施、支持、必要特征、效果或修改依据等的影响，不以关键词判级 |
| `issue_origin` | `inherited`或`current_node`，继承项注明首次节点与本次新判断，不把所有问题算本节点新造 |
| 纠正动作与确认状态 | 依据、所需人工动作、处理前提、剩余风险和提交使用影响 |

模拟审查质疑明确标记`simulation_not_official_oa`，关联具体问题、原文、可能的质疑理由、已有可回应依据和仍需材料；不伪造通知书、审查员观点、审查日期或实际OA证据。数量由真实风险决定，不为凑数制造质疑；材料不足则说明受限，不捏造决定性证据。

### 1.12 风险、持续输出与提交建议〔R12〕

**重大风险影响提交建议，不中止主Markdown生成。** 影响公开充分、必要技术特征、权项支持、技术效果或修改依据的重大问题必须进入“风险与待确认事项”；正式文本版本未定或关键材料无法核验导致无法完成决定性检查时，也要说明不建议直接提交的具体原因，而非伪称实质不合格。

每条全链警示保留`warning_id`、首次产生节点、继承来源、问题、受影响内容、当前处理、模型补齐情况、交付影响、建议人工动作，以及`open|confirmed|resolved|accepted`状态。全部开放警示向后继承；同类去重不能丢掉原ID、关联与来源。

`confirmed`不自动等于问题解决，`accepted`风险不自动等于技术缺陷消失；关闭或更新须有材料、技术修订或明确人工处理依据，记录关闭节点、依据、受影响内容及新状态，保留原警示和处理历史。报告生成、模型相信“问题不大”或无新信息不能关闭风险。

提交使用建议说明：已检查范围、重大问题/决定性缺口、可继续下游使用的边界、提交前必要动作及最终人工决定。没有检出问题不等于不存在问题；范围受限不作整套通过承诺。

需要返工只输出`recommended_rework_flow`、`affected_content`、`reason`、`recommended_action`、`expected_improvement`。可建议4-11处理权项、4-12处理说明书/图文，也可按问题来源建议更早节点；由人工决定，不建立自动回流。
